## 0. 贯穿性设计原则

即使 V1 是 fixture 规模、内存实现，**所有设计都为最终产品级架构预留可立即扩展的接口余量**。把未来会变化/会重的部分（持久化后端、异步作业队列、外部数据源）收敛到接口边界，V1 用最简实现填充，未来换实现时上层零改动。

已确立的同构范式：
- `SliceStore`：读召回 / 可变写回分离，V1 = `MemoryIndex`。
- `TaxonomyStore`（本设计新增）：只读 `Taxonomy` 视图 / 可变演化层分离。
- 回填执行体：设计上异步，V1 用可 await 的 async 方法填充，未来外包 job 队列 + worker。

## 2. 新增模块结构与数据模型

### 2.1 包结构


`TaxonomyStore` 新增于 `src/module0/taxonomy.py`（与只读 `Taxonomy` 并列，共享 `TaxonomyLabel`）。

### 2.2 数据模型（`src/module0_5/models.py`）

```python
@dataclass
class LabelProposal:
    """模块0 side-channel 产出，0.5 ② 的输入。仅来自 passed 子问题。"""
    label: str
    description: str
    parent: str | None                    # LLM 建议的父节点（可能不存在于现词表）
    description_embedding: list[float]     # compiler 用 self._embedding_model 算好
    keywords: list[str]
    source_sub_problem_id: str            # 溯源：哪个子问题提的（④ 回填优先级用）

@dataclass
class BackfillResult:
    """④ 回填执行体的显式返回（不抛穿，失败可读）。"""
    label: str
    candidates_screened: int              # Step 2 粗筛数
    judged_true: int                      # Step 3 精判命中数
    slices_written: int                   # Step 4 实际写回数
    errors: list[str]                     # LLM 失败等，可读不中断
```

- `LabelProposal` 刻意**自带 embedding**（决策：模块0 compiler 算），0.5 开箱即用不碰模型。
- `BackfillResult` 的显式字段服务"可被队列调度的作业"——幂等、失败可返回。
- 契约对齐：`LabelProposal` 经 ② 转成 `TaxonomyLabel`（taxonomy.py 已有，字段齐全），入库时补齐 `new_root` / `taxonomy_extension:true` / `created_at`。

## 3. ① 提议捕获（模块 0 开口子）

> **⚠ 行号基准（2026-07-10 复核更新）**：本 §3 的行号已按开源化 + 模块0健壮性两次重构后的 `compiler.py` 现状刷新。关键结构性事实不变，但 Call 1/2/3/2' 现均经 `_call_and_parse`（重试/None 防护）路由，`_clarify_and_reeval` 已返回 `list[SubProblem]`。采集机制据此调整为「就地汇总到 self」（见 §3.4/§3.5）。

### 3.1 现状与问题（精化后核对结论）

spec `2026-07-09` 的「事实 3」笼统称"提议元数据被丢弃"。核对代码后，缺口比原描述更靠上游，需分三层看清：

1. **prompt 输出格式无槽位（根因）**：Call 2 prompt 正文（`prompts.py:63`、冷启动分支 `prompts.py:128-134`）确要求 LLM 对新标签附 `description + parent + taxonomy_extension`，但**输出 JSON schema**（`prompts.py:78-90` 及冷启动分支 `prompts.py:145-157`）只定义了 `target_capability: ["label1"]` **纯字符串数组**——没有任何字段承载提议的 `description/parent`。LLM 即便遵从正文，也无处安放结构化提议。
2. **解析层其实不丢**：`parse_call2_response`（`parsing.py:104-125`）`return items`，返回 `json.loads` 的**完整 dict**，额外键天然保留、并不剥离。`required` 元组（`parsing.py:119-120`）只做存在性校验，不删字段。**注意**：Call 2/2' 现经 `_call_and_parse` 调用 `parse_call2_response`，该 helper 只加重试/None 防护、不剥字段，故 `label_proposals` 额外键仍能穿过。
3. **compiler 层才丢**：`_build_sub_problem`（`compiler.py:230`）只挑固定字段构造 `SubProblem`，未定义的提议键在此被弃。

因此 ① 的改动是**三处**：先给 prompt 输出格式开槽位（改动 1），解析层顺带保留（改动 2，基本零成本），compiler 采集并算 embedding（改动 3）。

### 3.2 改动 1 —— `src/module0/prompts.py`（输出格式开槽位，根因修复）

在 Call 2 与 Call 2' 两个分支的输出 JSON schema 中，为新标签提议增加**结构化槽位**（可选字段，仅当 LLM 提议新标签时填）：

```jsonc
{
  "id": "p1",
  "target_capability": ["label1"],
  // ...现有字段不变...
  "label_proposals": [                    // 新增，可选。无新提议时省略或空数组
    {"label": "new_label", "description": "一句话中文", "parent": "父建议或null", "keywords": ["kw1"], "taxonomy_extension": true}
  ]
}
```

同步在 prompt 正文明确："提议新标签时，除在 `target_capability` 中使用该标签名外，**必须**在 `label_proposals` 数组补齐其 `{label, description, parent, keywords, taxonomy_extension:true}`。"两个分支（有词表 / 冷启动空词表）都要改。

### 3.3 改动 2 —— `src/module0/parsing.py`（保留提议，不破坏现有校验）

- `parse_call2_response` 返回结构与 `required` 校验**保持不变**（`label_proposals` 是可选字段，**不进 `required`**——避免没有新提议的正常 item 被误判缺字段）。
- 由于解析层本就返回完整 dict，`label_proposals` 键天然被保留——本改动主要是**显式确认并加测试锚定**，几乎零代码。
- 解析层只做"存在即保留"，不做语义判定（判定属 0.5 ②）。

### 3.4 改动 3 —— `src/module0/compiler.py`（就地采集 + 算 embedding + side-channel 暴露）

复用现有 `hyde_embeddings` 的 side-channel 范式，新增两个属性——一个内部累积器、一个最终产出：

```python
def __init__(self, ...):
    ...
    self.hyde_embeddings: dict[str, list[list[float]]] = {}
    self.label_proposals: list[LabelProposal] = []       # 最终产出，side-channel
    self._collected_proposals: list[dict] = []           # 内部：就地累积的原始提议 dict
```

**采集机制（重构后：就地汇总到 self）**。重构后 `c2_results` 只在 `compile()` 内可见、`c2p_results` 被封装在 `_clarify_and_reeval` 内，二者不再同时可见。因此改为**在每批 result 被消费处就地采集**：

1. **主路径 Call 2**：在 `compile()` 遍历 `c2_results` 的路由循环里（`compiler.py:119` 起），对**最终判为 passed** 的 item，把其 `label_proposals`（携 `source_sub_problem_id`）追加进 `self._collected_proposals`。
2. **澄清路径 Call 2'**：在 `_clarify_and_reeval`（`compiler.py:190`）遍历 `c2p_results` 构造 `recovered` 的循环里（`compiler.py:218` 起），对最终 recover 的 item 同样就地追加进 `self._collected_proposals`。
3. **统一算 embedding**：在现有 embedding 循环（`compiler.py:154-157`）之后，用**同一个** `self._embedding_model` 给累积的提议算 description embedding，产出最终 `LabelProposal`：

```python
# 现有 embedding 循环之后：
if self._embedding_model is not None:
    for prop in self._collected_proposals:
        prop_obj = LabelProposal(..., description_embedding=self._embedding_model.embed(prop["description"]))
        self.label_proposals.append(prop_obj)
```

**关键**：只采集**最终 passed / recovered** 的 item（drop 掉的不采），这与「仅 passed 子问题贡献提议」的决策一致——因为采集点就在"判定为 pass/recover 之后"，drop 的 item 根本不进入采集分支。

### 3.5 关键设计点

- `compile()` 返回值 `ProblemSpec` **不变**（契约冻结）；提议只走 side-channel，与 `hyde_embeddings` 同构，不污染契约。
- `compile()` 开头需重置 `self._collected_proposals = []` 和 `self.label_proposals = []`（与 `dropped_records`/`hyde_embeddings` 重置一致，每次运行独立）。
- **就地采集取代原「统一 `_extract_proposals(sp, c2_results, c2p_results)` 反查」**：重构后两批 result 不再同时可见，就地采集在每批消费处进行，天然只覆盖 passed/recovered，无需反查、也无需改 `_clarify_and_reeval` 的返回签名（它继续返回 `list[SubProblem]`；提议通过 `self._collected_proposals` 副作用累积）。
- embedding 仅在 `self._embedding_model is not None` 时算（与现有 hyde 逻辑一致）；无模型时提议原始 dict 仍被采集到 `_collected_proposals`（description_embedding 留空，测试可注入）。
- 契约 §6「三处 embedding 同模型同维度」由结构保证：description embedding 与 hyde embedding 用**同一实例、同一次运行**产出。

### 3.6 测试

- 注入假 gateway 返回带 `label_proposals` 的 Call 2 响应 → 断言 `compiler.label_proposals` 捕获 `{label, description, parent, keywords}`。
- 断言 drop 掉的 item 的提议**不**被采集。
- 注入假 `embedding_model` → 断言 `description_embedding` 被填充。
- prompt 输出格式回归：断言两个分支的 schema 均含 `label_proposals` 槽位说明。

## 4. ② 去重 + 挂载判定 + `TaxonomyStore` 入库

### 4.1 `TaxonomyStore`（新增于 `src/module0/taxonomy.py`）

职责：持有可变词表状态，承担入库 / version 递增 / save / 产出只读快照。契约 §5.3 三条规则（新标签入库、去重检查、挂载判定）在此落地。

```python
class TaxonomyStore:
    """可变演化层。Taxonomy 保持只读；本类为唯一写入点。"""
    def __init__(self, taxonomy: Taxonomy): ...           # 从只读视图起步
    def snapshot(self) -> Taxonomy: ...                   # 产出只读快照供 prompt 注入
    def existing_labels(self) -> list[TaxonomyLabel]: ... # 供 ② 算余弦
    def add_label(self, label: TaxonomyLabel) -> None: ... # 追加 + version patch+1 + 维护 _by_name
    def save(self, path) -> None: ...                     # 写回 §5.2 结构的 JSON
```

- `Taxonomy` 只读、`frozen` 不动；`TaxonomyStore` 是唯一写入点。读路径复用 `snapshot().to_prompt_text()`。
- `add_label` 内部维护索引一致性、`version` patch +1（§5.3「不影响已有条目」）。

### 4.2 去重 + 挂载判定（`src/module0_5/evolution.py`）

纯函数式判定，判定与写入分离（便于单测）：

```python
def resolve_proposal(
    proposal: LabelProposal,
    existing: list[TaxonomyLabel],
    *,
    dedup_threshold: float = 0.85,   # 契约 §5.3
    mount_threshold: float = 0.60,   # 契约 §5.3
) -> ProposalResolution:
    """判定：重复→映射已有 / 新叶子→挂父 / 新顶层→new_root。零写入。"""
```

`ProposalResolution` 三种结果：

| 结果 | 触发条件 | 动作 |
|------|----------|------|
| `duplicate` | 与某已有标签 `description_embedding` cosine **> 0.85** | 映射到该已有标签，**不入库**（返回映射目标名）；**不触发回填** |
| `new_leaf` | 非重复，且与某候选父节点 cosine **≥ 0.60** | 挂相似度最高父节点下，`parent=该父`，`new_root=false` |
| `new_root` | 非重复，且所有候选父 cosine **< 0.60** | 创建新顶层，`parent=null`，`new_root=true` |

### 4.3 关键设计点

- **判定 vs 写入分离**：`resolve_proposal` 零副作用，只返回决策；编排层拿决策调 `TaxonomyStore.add_label`。去重/挂载逻辑可脱离 store 单测。
- **候选父口径（已定）**：挂载相似度与现有**顶层节点**（`parent is None` 的标签）的 `description_embedding` 算 cosine，**以 embedding 相似度为准**（契约 §5.3 把挂载定义为余弦 ≥0.6，是硬规则）。proposal 的 `parent`（LLM 建议）仅在 cosine 接近时作 tie-break 参考，不凌驾于契约；且 LLM 建议可能指向不存在的节点，不能作为权威。
- **`created_at` 时间戳**：本代码库约定纯逻辑内不可用 `Date.now()`/`datetime.now()`；时间戳由编排层（脚本）注入，`resolve_proposal` 与 `add_label` 不自行产生时间。
- **duplicate 处置**：丢弃不回填（决策）。仅 new_leaf/new_root 进 ④。

### 4.4 测试

- 构造已知 embedding 的现有标签 + 提议 → 断言三分支（cosine>0.85 映射 / ≥0.6 挂最相似父 / <0.6 新顶层）。
- `TaxonomyStore.add_label` 后 version patch +1、`snapshot()` 能查到新标签、已有条目不受影响。

## 5. ③ 继承降权后置重排（`src/module0_5/inheritance.py`）

### 5.1 要解决的场景

新叶子标签刚经 ② 入库、④ 回填尚未完成时，查询它不至于空手——用 taxonomy 树把"标了其父/兄弟叶子"的历史切片以 ×0.3 捞回来兜底。这是**回填完成前的过渡态**，非最终状态。

### 5.2 集成方式（0.5 侧后置重排，recall 不改）

```python
def rerank_with_inheritance(
    hits: list[RecallHit],           # store.recall() 原样返回的候选
    *,
    target_label: str,               # 查询针对的新叶子标签
    taxonomy: Taxonomy,              # 只读快照，提供父子映射
    exact_weight: float = 1.0,
    inherited_weight: float = 0.3,   # 契约 §5.3 值
) -> list[RecallHit]:
    """对已召回候选做基于 capability_labels + taxonomy 树的加权重排。零 LLM。"""
```

### 5.3 打分逻辑（对每个 hit，读其 `signature.capability_labels`）

| 切片状态 | 判定 | 权重 |
|----------|------|------|
| `capability_labels` 含 `target_label` 本身 | 精确命中（回填已覆盖） | ×1.0 |
| 不含本身，但含 `target_label` 的**父节点或兄弟叶子** | 继承兜底 | ×0.3 |
| 都不含 | 仅靠 BM25/向量召回分 | ×1.0（不额外加成也不惩罚） |

- 权重作用在 `hit.rrf_score` 上，重排后返回。最终分 = `rrf_score × 继承权重`，与契约 §5.3「向量/BM25 召回分主导 + 标签信号调制」一致。
- 父子映射从 `taxonomy` 只读快照现算（`target_label` → `parent` → 该 parent 的所有子叶子）。切片只存叶子标签，查询时反查——印证「`capability_labels` 只存叶子」的决策。

### 5.4 关键设计点

- 纯函数、零副作用、零 LLM、不碰 `MemoryIndex`；模块 1 的 209 passing 一行不动。
- 候选池要给够（`recall` 的 `top_n` 足够大），否则该被 ×0.3 捞回的父节点切片没进候选。**已定**：`top_n` 默认 200（与 §6.1 backfill 的 `top_k` 对齐），设为可调参数；fixture 规模不敏感，产品级按语料规模调参。
- **③ 与 ④ 是同一打分逻辑的两个时间点**：回填完成后同一批切片带上 `target_label` 本身，自然从 ×0.3 升级为 ×1.0，无需切换代码路径。

### 5.5 测试

- 构造切片 A 标 `target_label`、B 标其父、C 无关 → recall 后 rerank → 断言 A(×1.0) 排在 B(×0.3) 前、B 非零进入结果、C 不受额外加成。
- 回填后给 B 补上 `target_label` → 再 rerank → B 升到 ×1.0。

## 6. ④ 异步回填执行体（`src/module0_5/backfill.py`）

### 6.1 执行体签名

设计上异步，V1 用可 await、幂等、输入输出显式、失败可返回的 async 执行体填充接口边界。它是"一个可被队列调度的作业"，不是队列本身。

```python
async def run_backfill(
    new_label: TaxonomyLabel,        # ② 刚入库的 new_leaf/new_root
    store: SliceStore,               # 注入（读候选 + 写回）
    judge: Judge,                    # 复用模块1 Judge
    *,
    top_k: int = 200,                # Step 2 粗筛量，可调 seam
    judge_batch_size: int = 30,      # Step 3 batch，契约建议 20-50
) -> BackfillResult:                 # 显式返回，不抛穿
    """4步回填一个标签。幂等：已标该 label 的切片跳过。"""
```

### 6.2 四步（全部对接 `SliceStore`，可在 `MemoryIndex` 上完整单测）

```
Step 1 构造回填查询（零LLM）：
        new_label.keywords → BM25；
        new_label.description_embedding → 向量查询锚；
        结构化过滤留空/宽松
Step 2 粗筛（零LLM）：store.recall(...) 取 top_k 候选切片
Step 3 LLM 精判（batch）：judge.judge_batch 判"该切片是否演示了此能力"，
        20-30/batch，结构化布尔；失败记入 errors[] 不中断
Step 4 写回：judged_true 的切片 → store.update_labels(traj_id, idx, [new_label.label])
        （update_labels 已是合并语义，天然幂等）
```

### 6.3 产品级余量落点

- **幂等**：Step 4 用已合并语义的 `update_labels`（重复回填不重复加标签）；Step 2 可先跳过已标该 label 的切片。作业重跑安全 → 队列 at-least-once 投递无副作用。
- **失败可返回**：LLM 失败进 `BackfillResult.errors`，不抛穿。worker 可据此重试/告警。
- **无隐藏全局状态**：store/judge 全注入，`run_backfill` 是纯执行体。未来在**外层**包 job 队列 + worker + 优先级排序（按新标签关联问题数），`run_backfill` 一行不改。

### 6.4 测试

- 在 `MemoryIndex` 上跑完整 4 步：入库 → ③ 兜底非空 → ④ 回填后 `recall` 精确升权。
- 幂等：重跑 `run_backfill` 不重复加标签。
- LLM 失败进 `errors` 不中断。

## 7. 触发编排（V1 形态）

spec §5.6 的离线链路，V1 用直接 await 串起：

```
模块0 compile() → label_proposals（side-channel）
    │
    ▼  对每个 proposal：
② resolve_proposal → duplicate:丢弃 / new_leaf|new_root:TaxonomyStore.add_label + save
    │  （入库即时，查询立即可用）
    ▼
③ 查询期：rerank_with_inheritance 兜底（×0.3），回填完成前的过渡态
    │
    ▼  异步（V1 直接 await，未来投队列）：
④ run_backfill(new_label, store, judge) → update_labels 写回 → 升级为 ×1.0
```

- ② 入库是**同步快操作**（查询立即可用）；④ 是**解耦的慢作业**。
- V1 编排层顺序 await，但二者接口边界清晰分离——这就是"预留异步边界"。
