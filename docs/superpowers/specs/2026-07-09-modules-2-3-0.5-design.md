## 1. Context

`SWE轨迹优选器设计.md` 定义 6 个模块（0 / 0.5 / 1 / 2 / 3 / 4）。核对源码后确认：已实现 0、1；未实现 2、3、0.5；模块 4 第一版不做。

从 Problem Spec 到最终可交付的 SFT 数据集（N 条）这段链路——软加分精排、去重、覆盖度优选、配比——目前是空的。本规格补齐这三个模块的**完整架构**（非最小可跑版）。本阶段仍是 fixture 规模验证链路，不引入生产级持久化。

### 1.1 探查中发现的三处关键事实（决定架构，非小问题）

> 这三条都是**已经存在于代码里的现状**，不是 bug 报告。逐条按「现状 → 为什么成为问题 → 本设计怎么处置」拆开，处置动作的完整版在正文对应章节。

#### 事实 1：模块 1 的 judge 已经做了设计里"模块 2 的语义匹配核心"

- **现状**：`pipeline.py:156` 的 `judge_batch` 针对 `target_capability + trajectory_signal` 调 LLM，输出 `match / confidence / loss_mask_spans`。这正是设计文档分配给模块 2 的"语义能力匹配"职责——现在它已经在模块 1 里跑了。
- **为什么成为问题**：
  - 判定是**硬过滤**（`pipeline.py:165`：`if jr.match and jr.confidence >= min_confidence`）——不匹配的切片被直接丢弃。但设计优化⑤要求改成**软加分**（未命中 ×0.3 衰减而非砍掉），以降低 judge 打标噪声导致的误杀。
  - 召回阶段算出的 **RRF 融合分被扔掉了**（`index.py:88`：`recall()` 只返回 `sig`，丢弃 `_score`）。模块 2 的 relevance 公式需要这个分数当基数，现在拿不到。
- **本设计处置**：模块 1 的 recall+judge 保留，但（a）`recall()` 改为带回 RRF 分（§2.1 `RecallHit`）；（b）硬过滤删除，改由模块 2 做软加分排序（§3）。即：模块 2 不重新发明能力匹配，而是**复用 judge 结果 + 召回分**做评分层。

#### 事实 2：内存索引每次 `run()` 重建，没有存量语料

- **现状**：`pipeline.py:71` 每次 `run()` 都 `self._index = MemoryIndex()`，索引是一次性的，跑完即弃。
- **为什么成为问题**：模块 0.5 的 targeted backfill 要"把新标签**写回**已有切片的 `capability_labels`"。写回的前提是存在一批**长期存活的语料**。对每次重建的内存数据写回是空操作——下次 run 就没了，没有存量可回填。
- **本设计处置**：**不现在上真实持久化**（本阶段是 fixture 规模）。改为抽出 `SliceStore` 接口，把可变写回收敛到 `update_labels` 这一个 seam（§2.1）。V1 仍用 `MemoryIndex` 实现——backfill 的**编排逻辑**因此可以在内存实现上完整跑通和单测（入库→回填→`recall` 看到升权），而真实持久化后端作为后续单独任务替换实现类即可，模块 2/3/0.5 一行不改。

#### 事实 3：模块 0 生成了新标签提议元数据，但丢弃了

- **现状**：Call 2 的 prompt（`prompts.py:65` 及冷启动分支 `prompts.py:129-132`）已经要求 LLM 对新提议的标签附带 `description + parent + taxonomy_extension:true`。但 `parse_call2_response`（`parsing.py:117`）只校验并保留 `target_capability`，`compiler.py` 最终把标签存成**裸字符串列表**，提议的元数据在解析环节被丢掉。
- **为什么成为问题**：模块 0.5 的第一步 ①（新标签提议捕获）需要拿到这些 `{label, description, parent}` 元数据作输入。现在 LLM 明明产出了，却没有任何代码接住——**0.5 ① 的上游生产者是缺失的**。
- **本设计处置**：在模块 0 开一个口子——扩展解析层捕获提议元数据，`compiler` 通过 side-channel（类比现有 `hyde_embeddings`）把 `label_proposals` 连同 ProblemSpec 一起暴露出来，供 0.5 ② 去重挂载消费（§5.1）。

### 1.2 五项已确认的架构决策

| # | 决策 | 选择 |
|---|------|------|
| 1 | 模块 2 定位 | **薄排序层，复用 judge**。不再独立打 capability_labels 作主匹配。 |
| 2 | 存储后端 | **抽象 `SliceStore` 接口 + `MemoryIndex` 作 V1 实现**，本次不做真实持久化后端。 |
| 3 | relevance 公式 | `relevance_score = RRF融合分 ×(judge.match ? 1.0 : 0.3)`；`judge.confidence` 存作质量参考，不进排序。 |
| 4 | 模块 0.5 范围 | **①②③④ 全部完整架构**，含 targeted backfill 4 步，对接 `SliceStore.update_labels`。 |
| 5 | 模块 3 通用数据 | **暂无数据源，只留配置化拼接钩子**（比例参数 + 数据源路径），不实现数据源本身。 |

## 2. 存储抽象层（贯穿三模块的地基）

模块 2/3/0.5 全部对接口编程，不碰具体实现。**接口本身是交付物；真实后端（ES/Qdrant 或 SQLite+faiss）为后续单独任务。**

### 2.1 `SliceStore` 接口（新增 `src/module1/store.py`）

```
class SliceStore(Protocol):
    def add_batch(sigs: list[TrajectorySignature]) -> None
    def recall(*, structured_filters, keywords, query_embeddings, top_n)
        -> list[RecallHit]           # 关键改动：带回 RRF 融合分
    def get_slice(trajectory_id, slice_index) -> Slice | None
    def update_labels(trajectory_id, slice_index, labels: list[str]) -> None  # 可变回写 seam（0.5 唯一落点）
```

- `RecallHit = (signature, rrf_score)`：现 `recall()` 丢弃融合分，模块 2 需要它。改为返回 `(sig, score)` 对。
- `MemoryIndex`（现 `src/module1/index.py`）实现该协议：补齐 `get_slice`（现由 `pipeline._slice_map` 承担，下沉进 store）、`update_labels`（改内存字段）；`recall/add_batch` 已就位，仅调整返回类型。
- V1 语义不变：`update_labels` 在内存实现里真的改字段，回填后 `recall` 真能看到升权——**回填编排逻辑可在内存实现上完整单测**。

### 2.2 数据模型改动（`src/module1/models.py`）

- `TrajectorySignature` 增加 `capability_labels: list[str] | None = None`（0.5 ③④ 的物化字段；judge 是事实源，缓存/回填写入它）。

## 3. 模块 2：相关性精排（单闸门）

### 3.1 定位

模块 1 的 recall + judge 保留，但**产出物下沉为"带分候选"**，模块 2 是紧接其后的评分/排序层。核心改动：把当前的**硬过滤**改为**软加分**（设计优化⑤）。

### 3.2 数据流

```
recalled_hits (RecallHit: sig + rrf_score)  ← 模块1召回，带回融合分
    │
    ▼
① judge_batch（复用模块1现有 Judge）→ 每切片 match/confidence/spans
    │
    ▼
② 软加分（不再硬砍）：
     relevance_score = rrf_score ×(judge.match ? 1.0 : 0.3)
     judge.confidence → 存入 matched_problem 作质量参考（不进排序）
     capability 命中缓存：judge.match 的切片，其 target_capability 经 store.update_labels 缓存回写（下次免判）
    │
    ▼
③ 按 relevance_score 降序，取 top-N → 交付模块 3
```

### 3.3 输出模型（新增 `ScoredCandidate`）

当前 `SFTCandidate` 按 `trajectory_id` 合并（`pipeline.py:92`），**丢失了切片粒度**——但模块 3 的 submodular 在**切片**上做覆盖优选。因此模块 2 输出改为**扁平的切片级带分记录**：

```
@dataclass
class ScoredCandidate:
    trajectory_id: str
    slice_index: int
    trajectory_path: str
    sub_problem_id: str
    capability: list[str]
    relevance_score: float          # 排序键（模块3 submodular 消费）
    judge_confidence: float         # 质量参考
    loss_mask_spans: list[dict]
    embedding: list[float]          # 复用签名 embedding，供模块3去重/多样性，零额外成本
```

- 一个 (slice, sub_problem) 一条。同一切片命中多个子问题 → 多条（模块 3 覆盖度需按子问题归属）。

### 3.4 关键文件

- 新增 `src/module2/rerank.py`：`rerank(hits, judge_results, sub_problem) -> list[ScoredCandidate]`。
- `src/module1/index.py`：`recall()` 返回 `RecallHit`（带 rrf_score）。
- 编排：`pipeline.py` 的 `_process_sub_problem` 拆分——recall+judge 留模块 1，评分/软加分调用模块 2。硬过滤（`pipeline.py:165`）删除，改软加分。

## 4. 模块 3：集合优选（零 LLM）

输入模块 2 的 `ScoredCandidate` 列表（百~千级，跨多个子问题）+ Problem Spec 子问题结构。输出最终 SFT 数据集（N 条）。全程纯算法。

### 4.1 步骤 1：语义去重（`src/module3/dedup.py`）

- 两层：MinHash/SimHash 抓近乎逐字重复（token 级，快）；embedding cosine > 0.95 抓语义重复（用 `ScoredCandidate.embedding`，零额外成本）。
- 一组重复保留 `relevance_score` 最高者。

### 4.2 步骤 2：submodular 覆盖优选（`src/module3/selection.py`，核心）

facility location 贪心，预算 N：

```
f(S) = Σ_p min(cover(p,S), cap_p) + λ·diversity(S)
cover(p,S)  = Σ 属于子问题 p 的切片 relevance_score
cap_p       = 单子问题覆盖上限（如 N/子问题数 ×2），防堆积
diversity(S)= S 内 embedding 两两距离和，鼓励语义分散
```

- 约束：总数 = N（硬）；`min_per_problem`（如 max(5, N/子问题数/2)）防低分子问题饿死；`cap_p` 防高分子问题独占。
- 贪心递减收益 → 天然同时解决覆盖均匀 + 多样性。保证 ≥ (1-1/e) 最优。

### 4.3 步骤 3：配比与掺通用数据（`src/module3/compose.py`）

- 难度配比：用免费信号（turn_count / step_count）做难度代理，隐含在 diversity 项 + 后置偏斜检查。
- **掺通用数据：仅配置化拼接钩子**（决策 5）——`GeneralDataConfig(ratio=0.2~0.3, source_path=None)`。`source_path` 为空时跳过并 log，不实现数据源。定向切片 70-80% + 通用占位 20-30% 的**拼接逻辑**完整，数据源留待第二版。

### 4.4 关键参数

`N`（总预算）、`cap_p`、`min_per_problem`、`λ`、通用数据比例 + 路径。

## 5. 模块 0.5：标签系统演化（①②③④ 全部完整设计）

新增 `src/module0_5/`。核心矛盾：新标签出现后历史切片无该标签会漏召回，全量重打不可接受。

### 5.1 ① 新标签提议捕获（需在模块 0 开口子）

当前提议元数据被丢弃。改动：

- `src/module0/parsing.py`：新增 `parse_call2_labels()`（或扩展 `parse_call2_response`）捕获每个 `taxonomy_extension:true` 标签的 `{label, description, parent, taxonomy_extension}`。
- `src/module0/compiler.py`：`compile()` 收集提议到 `self.label_proposals`，随 ProblemSpec 一并暴露（side-channel，类比现有 `hyde_embeddings`）。
- 每个提议补 `description_embedding`（用 `self._embedding_model` 对 description 编码，同契约 §4 模型 1024-d）。
- 新增 `LabelProposal` 数据模型：`{label, description, parent, description_embedding, keywords, taxonomy_extension, created_at}`（对齐契约 §5.1 `TaxonomyLabel`）。

### 5.2 ② 去重 + 挂载判定（`src/module0_5/evolution.py`）

- **去重**：提议 `description_embedding` 与已有标签 cosine > 0.85 → 视为重复，映射到已有标签，不入库（契约 §5.3）。
- **挂载**：与已有父节点 cosine ≥ 0.6 → 挂相似度最高父节点下作新叶子；均 < 0.6 → 创建新顶层（`new_root: true`），森林结构。
- 产出 `TaxonomyLabel` 条目，追加进 `labels[]`，version patch +1，不影响已有条目。

### 5.3 ③ 继承降权查询（`src/module0_5/inheritance.py`，query-time 融合）

解决"新标签入库还没回填时查询不返回空"。

- 查询新叶子标签时，把**标了其父节点**的切片也纳入候选，排序时 ×0.3。
- 依赖：`TrajectorySignature.capability_labels` + taxonomy 树遍历（父→子映射）。
- 融合：精确标新子标签（×1.0）+ 只标父标签（×0.3）+ 向量/BM25 召回分主导。
- 这是**回填完成前的过渡**，不是最终状态。

### 5.4 ④ 异步回填 targeted backfill（`src/module0_5/backfill.py`，4 步）

对接 `SliceStore`，编排逻辑可在 `MemoryIndex` 上完整单测：

```
Step 1 构造回填查询（零 LLM）：标签 keywords（BM25）+ description_embedding（向量）+ 语义推断的结构化过滤
Step 2 粗筛候选（零 LLM）：store.recall(...) 取 top-K
Step 3 LLM 精判（batch）：复用模块1 Judge，判"该切片是否演示了此能力"，structured output 布尔数组，20-50/batch
Step 4 写回：judged_true 的切片 → store.update_labels(traj_id, slice_index, [+new_label])
```

- 回填全程不阻塞查询：回填前走 ③ 继承降权兜底，回填后升级为 ×1.0 精确命中。
- 回填优先级按新标签关联问题数排序。

### 5.5 词表可变层（`TaxonomyStore`）

现 `Taxonomy`（`src/module0/taxonomy.py`）是只读视图。0.5 需要可变写回：新增 `TaxonomyStore`（或给 `Taxonomy` 加 `add_label()` + `save()`），承担 ② 的入库、version 递增、去重挂载写入。读路径复用现有 `to_prompt_text()` 等。

### 5.6 触发编排

0.5 是**离线/异步**流程，不在查询热路径：模块 0 编译产出提议 → ②去重挂载入库（即时，查询立即可用，走③继承兜底）→ ④后台回填（异步，完成后精确升权）。

## 6.5 实现顺序（已确认）

分两批落地，模块 0.5 依赖第一批的产出物（精确标签只有 2+3 消费），故排后：

**第一批 — 2+3 主链路（先做）**：打通 "Problem Spec → SFT 数据集(N 条)" 可交付链路。
1. `SliceStore` 接口 + `MemoryIndex` 补齐（含 `recall()` 改返回类型，见 §7 注）。
2. 模块 2 软加分 `rerank` + `ScoredCandidate`；`pipeline._process_sub_problem` 硬过滤改软加分。
3. 模块 3 去重 → submodular → 配比钩子。

**第二批 — 0.5 标签演化（后做）**：①提议捕获 → ②去重挂载 → ③继承降权 → ④异步回填。第一批的 `capability_labels` 物化字段 + `SliceStore.update_labels` seam 已在第一批就位，第二批直接消费。
